# 真实模型评测记录（2026-11-04）

本文记录第一次用真实模型执行 `evals/cases.jsonl` 的结果。**60 个案例中实际执行 31 个**，
另外 29 个没有运行，下文所有比例都只针对已执行的案例，不能外推为 60 例的结果。
原始轨迹在本地 `data/evaluation/runs/`（已被 `.gitignore` 排除），汇总目录为
`data/evaluation/runs/merged-20261104/`。

## 被测对象与方法

- 被测：默认的多 Agent 模式（Supervisor + 订单/物流/售后专业 Agent），聊天模型 `qwen3.8-max`，
  Embedding `qwen3-vl-embedding`，Rerank `qwen3-rerank`，网页降级关闭。
- 隔离：每个案例在独立临时目录中装配服务，checkpoint、画像、售后、工单、RAG 均为副本；订单、
  物流、政策来自只读夹具库，不读写 `data/` 下的业务库。
- 故障注入：在执行边界替换组件，不依赖模型“恰好”出错。例如专业 Agent 超时替身、Supervisor
  分阶段替身、规则服务不可用替身、SQLite 外部写锁、售后记录提交后抛出进程级异常再重启重放。
- 判分：`评委模型逐条核对 expected / forbidden` 与 `程序断言` 都通过才算 pass。程序断言包括：
  未确认轮次的售后/工单写入为零、用户 B 数据不出现在用户 A 的回复中、故障任务状态与重试次数、
  幂等写入条数等。评委与被测是同一模型（temperature=0），存在自评偏差，因此 31 例全部做了人工复核。
- 执行：同一天分三次运行，代码相同（`smoke-1`、`smoke-2`、`full-20261104`），并发 3～4 个案例。
  全量运行在完成 21 例后为控制费用手动停止；每个案例只取一次已判分结果，没有重跑挑选。

脚本：[runner.py](../src/customer_service_agent/evaluation/runner.py)。

### 人工复核

- 31 例的评委结论均与人工判断一致。
- ORD-012（失败）：两单状态和金额都正确，但没有说明 1011 尚无运单，按题目要求判失败合理。
  原因是汇总阶段丢掉了“无运单”这一事实。
- MUL-007（通过）：按题目要求通过，但第一轮其实是 Supervisor 规划调用 90 秒超时，直接返回
  “暂时无法安排客服任务”。题目只要求第一轮零写入，因此没有扣分；这是一个真实的稳定性问题。

## 耗时与调用量

统计非故障案例的 25 个正常轮次（端到端，含规划、专业 Agent、汇总；并发 3～4 个案例下测得）：

- 每轮耗时：P50 61.3 秒，P95 129.3 秒，均值 71.9 秒。
- 每轮平均 6.0 次模型调用，输入约 15.1k tokens，输出约 2.6k tokens（含推理 tokens）。
- 耗时随参与的专业 Agent 数增长：1 个 Agent 中位 30.8 秒，2 个 78.2 秒，3 个 125.9 秒。
- 三次运行共 206 次模型调用，输入约 51 万 tokens，输出约 8.7 万 tokens。

## 发现的问题与改进方向

1. **耗时过长**：P50 约 1 分钟。主要来源：
   - 25 个轮次中 18 个由订单 Agent 顺带调用 `save_customer_profile`，纯查询也多一轮工具往返；
   - 11 个涉及政策的轮次全部同时调用了 `lookup_policy` 和 `search_knowledge_base`，重复检索；
   - 订单 → 售后的依赖链串行执行，每个 Agent 又各自有工具循环；
   - `qwen3.8-max` 默认输出推理 tokens。
   可尝试：画像只在用户提供新资料时写入；政策检索二选一或合并；专业 Agent 换用较快模型或关闭思考；
   对单 Agent 能完成的简单查询跳过 Supervisor。
2. **规划超时整轮失败**（MUL-007 第一轮）：可缩短 Supervisor 超时并在超时后降级为单 Agent。
3. **汇总丢失否定事实**（ORD-012）：在汇总提示中要求保留“无运单/未找到”等否定结论。
4. **工具误用**：LOG-006 把运单号传给了 `lookup_order`，可在工具说明里区分订单号与运单号格式。

## 不能据此宣称的内容

- 60 例的通过率，或政策、多轮、安全三类的通过率。
- 秒级响应：实测单轮中位约 61 秒。
- 评委已与人工偏好校准：本次只做了 31 例的人工复核，评委与被测是同一模型。

## 复现

```bash
python -m customer_service_agent.evaluation.runner --cases ORD,LOG --workers 3
python -m customer_service_agent.evaluation.runner --retrieval-only
python -m customer_service_agent.evaluation.runner \
  --merge data/evaluation/runs/<run_a> data/evaluation/runs/<run_b> \
  --retrieval-from data/evaluation/runs/<retrieval_run> --run-dir data/evaluation/runs/merged
```

运行前会先探测一次聊天接口；账户欠费或密钥无效时直接退出，运行中遇到同类错误会停止派发后续案例，
受影响的案例记为 blocked，不计入通过或失败。
